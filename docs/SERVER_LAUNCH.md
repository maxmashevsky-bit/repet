# Запуск «Репет» на своём сервере

Подготовка владельцу от 2026-10-30. Публичное развёртывание не выполнялось. Общая изоляция преподавателей (16) и финальный аудит MVP (18) ещё не завершены: эта инструкция не объявляет платформу готовой к открытой регистрации детей.

## Что переносить

`sh scripts/package-server.sh` создаёт `tmp/server-bundle.tar.gz`. Внутри исходники, один корневой `Dockerfile`, `compose.prod.yml`, конфигурация прокси, миграции и инструкция. Нет `.env`, паролей, БД, загруженных пользователями файлов, `.git`, `node_modules`, локальных временных данных и тяжёлых референсных скриншотов дизайна. Учебные HTML из репозитория сохраняются. Архив не является резервной копией действующего сайта.

Dockerfile имеет цели `api`, `web`, `pdf-extractor`. Compose одной командой собирает их и запускает PostgreSQL и Caddy. Несколько процессов не объединены в один контейнер: PostgreSQL и небезопасные PDF/HTML остаются изолированными. [Многоэтапная сборка Docker](https://docs.docker.com/build/building/multi-stage/).

## Перед запуском

Нужен Linux с Docker Engine и Compose V2, диском для БД/файлов/копий, SMTP с STARTTLS (обычно 587), двумя разными именами хостов. Планировать минимум 4 ГБ RAM, для сборки предпочтительно 8 ГБ; это стартовый запас, не результат нагрузочного теста. Для HTML лучше отдельный регистрируемый домен. Не использовать тот же hostname с другим портом. Cookies приложения host-only, iframe sandbox, прокси HTML удаляет Cookie/Authorization.

Оба DNS-имени должны указывать на сервер; входящие TCP 80/443 и при необходимости UDP 443 должны доходить до Caddy. PostgreSQL и остальные сервисы не публикуют порты. Caddy получает/обновляет сертификаты автоматически, его тома нельзя удалять при обновлении. За CGNAT прямой вход не заработает: нужен публичный адрес/port forwarding либо отдельно согласованный туннель с проверенными лимитами и TLS. [Требования Caddy HTTPS](https://caddyserver.com/docs/automatic-https).

## Конфигурация

Распаковать архив в отдельный каталог сервера. Создать `.env.production` по `.env.production.example` и заменить все example-домены. В `secrets/` либо во внешнем `SECRETS_DIR` создать три файла, не добавляя их в Git:

| Файл | Содержимое |
| --- | --- |
| `db_password` | Собственный длинный случайный пароль PostgreSQL, одна строка |
| `database_url` | `postgres://repet:URL_ENCODED_PASSWORD@postgres:5432/repet?sslmode=disable`, тот же пароль, URL-encoded |
| `smtp_password` | Пароль/ключ SMTP, одна строка |

Каталог ограничить владельцем (`chmod 700 secrets`), файлы должны быть доступны UID 10001 только на чтение через Docker secrets; например, владельцу файла UID 10001 и режим 0400. Не делать весь репозиторий доступным всем на запись. Файлы secrets монтируются только нужным сервисам. Реальные значения здесь намеренно не создаются. [Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).

`SMTP_ADDR`, `SMTP_FROM`, `SMTP_USER` задаются в `.env.production`; SMTP_PASSWORD берётся из файла. У провайдера подтвердить домен отправителя и настроить SPF/DKIM/DMARC по его инструкции. Не использовать порт 465 с implicit TLS: текущий клиент требует STARTTLS. Доставка зависит от реального провайдера и DNS; локальный SMTP-тест не гарантирует попадание во входящие.

## Команды На Сервере

После заполнения конфигурации сборка и запуск одной командой:

```sh
docker compose --env-file .env.production -f compose.prod.yml up --build -d --wait
```

Раздельные команды для диагностики:

```sh
docker compose --env-file .env.production -f compose.prod.yml config --quiet
docker compose --env-file .env.production -f compose.prod.yml build
docker compose --env-file .env.production -f compose.prod.yml up -d --wait
docker compose --env-file .env.production -f compose.prod.yml ps
docker compose --env-file .env.production -f compose.prod.yml logs --tail=100 api web proxy
```

После запуска зарегистрировать тестовый аккаунт, получить письмо, перейти по ссылке, подтвердить адрес, открыть кабинет. До подтверждения API возвращает 403 `email_unverified`, даже если открыть страницу напрямую. Письмо действует час, повторная отправка — не чаще минуты. Токен хранится только хешем, ссылка использует URL fragment и не передаёт токен в access logs. Подтверждать нужно в браузере с сессией того же аккаунта. Ошибка SMTP не превращается в ложное сообщение об отправке; аккаунт сохраняется и позволяет повторить отправку. Старые аккаунты с неподтверждённой почтой также должны подтвердить адрес. В production отключить требование нельзя.

Локальная проверка почты без настоящего SMTP: обычный `compose.yml`, письма в Mailpit на `http://127.0.0.1:8025`. Подтверждение теперь включено по умолчанию и в development; только в изолированных тестах его можно явно отключить `REQUIRE_EMAIL_VERIFICATION=false`. Пустое или ошибочно написанное значение не отключает проверку, а останавливает запуск с ошибкой конфигурации. В этой рабочей сессии preview3020 использует отдельную тестовую БД; это не ваши прежние аккаунты и не production-данные. Mailpit не доставляет письма в интернет.

## Копии И Обновление

```sh
sh scripts/server-backup.sh
# Сохранить копию вне сервера; секреты хранить отдельно в защищённом хранилище.
# После проверки новых исходников и образов:
docker compose --env-file .env.production -f compose.prod.yml build
docker compose --env-file .env.production -f compose.prod.yml up -d --wait
```

Backup останавливает API/web на время согласованного снимка БД + приватных файлов и поднимает их через trap. Не запускать два backup одновременно. Для ежедневной копии настроить системный планировщик сервера на `sh scripts/server-backup.sh`, журнал и контроль свободного места; расписание на пользовательской машине не устанавливалось. Удаление старых копий и off-site sync настраиваются владельцем, не уничтожать единственный проверенный backup.

Восстановление **заменяет данные**, только на выбранном сервере после собственной копии:

```sh
sh scripts/server-restore.sh backups/TIMESTAMP --confirm-replace-data
```

Не выполнять `docker compose down -v`. Не пытаться подключить существующий PostgreSQL-том другой major-версии к PostgreSQL 16: переносить через dump/restore в новый том. Миграции применяются при старте API; при несовместимой миграции откат образа без восстановления БД недостаточен. Проверять восстановление в отдельном Compose project и затем вход/приватные вложения.

Логи ограничены 3 × 10 МБ на контейнер, health checks есть у БД/API/web/PDF; `/metrics` не проброшен прокси наружу. Внешний uptime/диск/сроки копий требуют отдельного мониторинга. Проверка CVE образов, нагрузочное испытание, пользовательские условия/согласия и полный сценарий 18 остаются условиями публичного запуска.

Локально проверены: три Docker target, Compose config, Caddy validate, работа standalone web с API/PG16/Mailpit/PDF, обе роли register→письмо→confirm→login, backup/restore БД + файла. Временный стек был только loopback и после проверок остановлен. Настоящие DNS/ACME/SMTP вне тестовой среды не проверялись.
