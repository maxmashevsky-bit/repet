# Постоянный процесс работы над «Репет 2.0»

Применяется к следующим задачам в этом репозитории. Сначала учитывать актуальный запрос пользователя и AGENTS.md; при конфликте явно назвать расхождение, не менять политику молча. Этот файл не разрешает автоматически реализовывать roadmap.

## Начало запуска

Исключение от 2026-10-29: пользователь явно разрешил последовательное выполнение очереди 08–19 и продолжение после обновления лимитов. Для этой очереди читать `CODEX_NEXT_RUN.md`, продолжать первый незавершённый шаг и после проверенного завершения переходить к следующему номеру. Прежние критерии одноимённых номеров не считать новыми DONE. Ограничения на push/deploy/PR/секреты сохраняются. После 19 остановиться.

1. Прочитать AGENTS.md, README.md, этот workflow, строки текущей задачи в CODEX_PROGRESS.md и соответствующие критерии REPET_ROADMAP.md. После этого читать только относящиеся к задаче файлы.
2. Выполнить `git status --short`. Запомнить существующие изменения. Не откатывать, не форматировать и не коммитить чужую работу. Если необходимое изменение пересекается с ней — сначала понять содержимое, сохранить его.
3. Показать пользователю текущую задачу и 3–6 конкретных шагов. Номер 00–19 — ссылка на этап, а не требование выполнять его целиком одним запуском.
4. Для начатой работы поставить IN_PROGRESS; записать дату и измеримые критерии текущего запроса. Не ставить весь этап DONE за выполнение небольшой части.

## Во время работы

- После существенного шага кратко сообщить результат и оставшуюся неопределённость. Не выводить большие исходники, полные логи и повторные планы.
- Переиспользовать компоненты и функции из раздела «Что переиспользовать» трекера. Не создавать второй API client, auth guard, Date helper или новую оболочку без причины.
- Сохранять Next.js/React/TypeScript и Go compatibility core; V2 внедрять по одному контексту через существующие контракты. Не менять архитектуру ради оформления.
- Проверять доступ отдельно для каждого ресурса, deny-by-default. Не принимать server-owned поля от клиента. Текущее расхождение регистрации с правилом role описано в ограничениях первоначального аудита (прежний критерий 05); смена назначения номера 05 не закрывает это расхождение и не разрешает расширять его на другие endpoints.
- Соблюдать бренд «Репет» и четыре верхних раздела. Не создавать отдельный route «Материалы».
- Не выполнять push, PR, deployment, публикацию, изменения GitHub settings. Проверка Docker не означает разрешение пересобрать и заменить запущенное приложение. Не перезапускать контейнеры ради аудита.
- Не создавать production credentials. Не читать и не выводить секреты без необходимости. Использовать тестовые данные и отдельную временную БД, не запускать изменяющие интеграционные тесты на пользовательской базе.
- Для нового кода добавлять проверки по риску изменения, а не тесты ради числа. Не реализовывать новые продуктовые функции в задаче аудита/документации.

## Проверки и доказательства

- Перед передачей результата запускать доступные `make test` и `make lint`. Дополнять typecheck/build/race, HTTP/browser, миграционными или контрактными проверками по области изменения и критериям этапа.
- Указывать точную команду, результат/exit code, дату, среду и покрываемый сценарий. Если проверялся Docker-образ, назвать это проверкой образа; не выдавать её за проверку текущих исходников без сравнения.
- Если TEST_DATABASE_URL отсутствует и PostgreSQL-тесты SKIP, это не успешная проверка интеграции. Отличать cached unit results от свежего прогона.
- Healthcheck доказывает доступность конкретного процесса, но не всю бизнес-функцию. Наличие frontend-кнопки не доказывает работу API; store-test не заменяет браузерный сценарий.
- Если команда недоступна, упала или зависла: записать конкретный этап и причину. При ограничении времени корректно остановить созданные процессы, не оставлять незавершённую проверку под видом PASS. Не скрывать ошибку через `|| true`.
- Для временных ресурсов записывать владельца и удалять только созданные этим запуском данные/контейнеры. Не удалять пользовательские volumes, БД, файлы и чужие процессы.

## Завершение

1. Сопоставить результат с критериями roadmap и текущего запроса. DONE — только при выполнении всех критериев. Частичная реализация или непроверенный критерий — IN_PROGRESS. BLOCKED — конкретное препятствие с понятным способом устранения. TODO — работа ещё не начата.
2. Обновить затронутые строки CODEX_PROGRESS.md: дата, проверенный результат, блокеры; дополнить доказательства и короткий журнал. Не переписывать даты других задач без новой проверки. Старые доказательства сохранять с датами или явно помечать как исторические.
3. Запустить `sh scripts/repet-progress.sh`, проверить согласованность 20 строк и `git diff --check`. Проверить diff: не попали секреты, временные данные и несвязанные изменения.
4. В конце кратко показать статус запроса, результаты проверок, проблемы и рекомендуемый следующий шаг. Не заявлять готовность всего «Репет 2.0» по числу DONE.
5. Остановиться. Не начинать следующий промпт, roadmap-этап или исправление вне согласованной задачи автоматически.

## Формат трекера

Таблица в CODEX_PROGRESS.md: `ID | Название | Статус | Дата проверки | Результат | Блокеры`. ID — ровно 00–19 по одному разу. Статус — TODO, IN_PROGRESS, DONE или BLOCKED. Не добавлять вертикальную черту внутрь ячеек; длинные доказательства выносить в раздел ниже. Отсутствие блокера обозначать явно, а не пустой ячейкой.

Сводка из любого текущего каталога:

```sh
sh /путь/к/репозиторию/scripts/repet-progress.sh
```

Без аргумента скрипт читает трекер относительно своего местоположения. Необязательный первый аргумент — другой файл такого же формата для проверки; скрипт не изменяет статусы, не запускает тесты и ничего не публикует.
